# Optional Google sign-in

Verified 2026-11-16 against `origin/main` ce769a0 and installed Go dependency sources before implementation. Google sign-in is disabled by default; configuration and ordinary Folio operation do not contact Google. A user explicitly starting login opens Google. Callback exchanges its authorization code and validates its signed identity token against Google's public keys.

## Operator configuration

Create a Google OAuth **Web application** client in Google Cloud Console. Register the exact `redirectURI` displayed in Folio administration: `<configured AppURL>/api/auth/google/callback`. Save its client ID and secret in Folio administration, then enable Google login. Client secret is AES-GCM encrypted by the installation data key and never returned, audited, or logged. Blank/omitted secrets retain the current secret.

Precreate each member in Folio before login; Google claims never create users or assign roles. Select Google-only for users without a local password. Password users can sign in through Google using an authoritative email match, while retaining their local password and any temporary-password change requirement. Their first successful Google login permanently binds canonical issuer and subject to the existing user ID. Different subjects cannot take over an already bound email, and bound subjects cannot move to a different email/user. Disabled accounts are denied. Google-only users have no password hash, temporary password, password-change gate, or password-reset path.

An empty hosted-domain list allows verified Gmail and Google Workspace accounts. A nonempty list permits only matching signed Google Workspace `hd` claims. An email suffix alone does not establish Workspace membership; putting `gmail.com` in the hosted-domain list does not permit consumer Gmail accounts. A third-party email Google account without `hd` is denied even when `email_verified` is true. Keep a password administrator for provider outages and OAuth client misconfiguration; the last administrator with an available login method cannot be removed by disabling Google or changing its domain policy. Google administrators count as an available fallback after a successful Google login; policy eligibility then uses their stored verified `hd`, so email domain aliases do not determine authorization. When no active password administrator remains, client ID/secret changes are refused to prevent a credential-switch lockout. Client-ID/secret correctness requires a real Google login; saving configuration does not contact the provider.

Google login retry friction is per opaque host-only HttpOnly browser cookie (Secure on HTTPS), ten starts per fifteen-minute window, reset on success. Clients can discard cookies, so this is soft friction. Hard resource bounds independently cap live five-minute pending states at 1,000 and concurrent token/JWKS exchanges at 16; an over-cap callback consumes its state before returning a safe retry error. Browser counters are limited to 10,000 entries by evicting the oldest, without denying all new visitors when the cache fills. Neither remote peer IP nor forwarded headers identifies users, so independent visitors through one local reverse proxy do not share a ten-start quota.

## Primary references

- [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect): authorization code flow, exact registered callback, state and nonce, stable subject, `openid email` scopes, Google issuer and token endpoints.
- [Google backend identity verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token): signature, audience, issuer, expiry, signed `hd` restrictions; Google is authoritative for Gmail or verified Workspace with `hd`, but third-party email ownership can change despite historical verification.
- [Google OAuth web server applications](https://developers.google.com/identity/protocols/oauth2/web-server): confidential web clients, registered callbacks and server-side code exchange.
- [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636): fresh high-entropy verifier, S256 authorization challenge, verifier in code exchange.
- [google.golang.org/api/idtoken v0.307.0 source](https://github.com/googleapis/google-api-go-client/blob/v0.307.0/idtoken/validate.go): `Validator.Validate` checks audience/expiry/signature and returns remaining claims. Folio separately enforces Google issuer, nonce, verified email, authority and hosted domain. It accepts only RS256 Google OIDC tokens before entering the generic validator. Installed source inspected at `$GOMODCACHE/google.golang.org/api@v0.307.0/idtoken/validate.go`.
- [golang.org/x/oauth2 v0.37.0 PKCE source](https://github.com/golang/oauth2/blob/v0.37.0/pkce.go): `GenerateVerifier`, `S256ChallengeOption`, `VerifierOption` used directly. Installed source inspected at `$GOMODCACHE/golang.org/x/oauth2@v0.37.0/pkce.go`.

## Implementation verification

`internal/server/google_auth_test.go` uses real RSA-signed test JWTs and a Config-injected HTTP transport serving the fixed token/JWKS endpoints. Tests cover default offline behavior, configuration secret redaction and encrypted persistence, session/CSRF requirements, exact scopes and callback, PKCE exchange, wrong browser/state/replay/expiry, nonce/issuer/audience/expiry/unverified/non-authoritative/precreated-account rejection, signed Workspace `hd`, subject binding, disabled users, Google-only password boundaries, pending-config invalidation, browser attempt limits, shared-reverse-proxy independence, bounded resource admission and provider network waits without the global mutation lock.

These deterministic integration tests verify Folio's protocol implementation. They do not claim a real Google account has completed consent; that requires the operator's registered client and browser login.
