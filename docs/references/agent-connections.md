Checked 2026-11-18 against Folio `origin/main` / HEAD `96d06c1abfd61394b8fb34c239c441b997b20ce0` and the current official client documentation. The connection UI lives in `web/src/AgentClientGuides.tsx`; shell commands are generated by `web/src/agentClientCommands.ts`.

## Folio authentication and process contract

`folio login --url URL --token-stdin` reads the token from stdin, validates it with `/api/me`, and saves the local CLI configuration (`cmd/folio/main.go:102–125`). `folio mcp` starts the stdio transport (`cmd/folio/main.go:127–128`). No token is included in the agent registration commands or Cursor JSON.

The CLI's default configuration is `folio/config.json` under Go's OS user configuration directory; `FOLIO_CONFIG` selects a different file (`internal/agent/client.go:30–35`). `FOLIO_URL` and `FOLIO_TOKEN` override saved values (`internal/agent/client.go:52–57`). The CLI creates its configuration directory with `0700` and writes the temporary configuration file with `0600` before renaming it (`internal/agent/client.go:63–87`). These are POSIX permission modes, not a claim about Windows ACLs. Agents must run under the same OS user/configuration context, or receive an explicit `FOLIO_CONFIG` path in their execution environment.

The macOS/Linux snippet launches Bash explicitly so its silent `read` behavior works from both Bash and zsh. It passes the token through stdin, clears the temporary variable, and preserves the login exit status. The URL is a separately shell-quoted positional argument. The Windows snippet uses `Read-Host -AsSecureString`, a temporary BSTR for stdin, and `finally` to release the allocation. See Microsoft's [Read-Host documentation](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.utility/read-host) and [SecureStringToBSTR](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.marshal.securestringtobstr).

Codex's add command selects stdio using `--` before the executable. Claude Code's user scope is explicit. Gemini's default scope is project, so the snippet requests user scope explicitly; `mcp` is an argument to the `folio` command.

VS Code's command writes editor-managed user-profile configuration. Windows PowerShell uses `--%` and escaped native JSON quotes, avoiding PowerShell's legacy native-argument quote removal. This follows Microsoft's [native argument and stop-parsing reference](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_parsing). The `code` executable was not installed in this verification environment; Windows runtime execution remains unverified.

Cursor uses different executables for the editor (`cursor`) and CLI (`agent`). Its guide provides a file-opening command and an additive JSON entry, rather than inventing a registration subcommand. Existing MCP servers must be retained. Neither Cursor executable was installed in the verification environment.

OpenCode documentation currently describes V2, while npm latest resolved to `1.19.6` during this check. Both accept the chosen stdio registration command. The shipped V1 CLI handles the name and trailing command at `mcp.ts:427–468` and writes the global configuration. The documentation's `--global` flag is absent from the shipped V1 help, so it is deliberately omitted. For explicit scope selection, the UI offers the verified interactive `opencode mcp add` workflow (`mcp.ts:474–535`). No existing OpenCode account or configuration was accessed or modified.

## Completion check and optional skills

After registration, request `folio_capabilities` from the agent. The tool returns installation capabilities and limits (`internal/agent/mcp.go:50–53`); a configured server entry alone does not prove authenticated tool access.

Optional skill commands are shown only for Codex and Claude Code: `folio skills install --client codex` and `folio skills install --client claude`. The CLI writes to `~/.codex/skills/folio/SKILL.md` or `~/.claude/skills/folio/SKILL.md`, respectively, and refuses to overwrite an existing file (`cmd/folio/main.go:327–358`). Skills supplement MCP registration; they do not authenticate the CLI.

`node --experimental-strip-types --test web/tests/agent_commands.test.ts` executes the displayed Bash login snippet in both Bash and zsh against a disposable stub. It checks literal URL handling with shell metacharacters, exact stdin delivery, no token on stdout, propagation of success/failure status, and the parsed VS Code JSON. PowerShell command generation is checked structurally; a Windows runtime check is still needed.

All 36 guide contrast states had zero axe color-contrast violations and no browser page errors. Desktop and mobile screenshots were visually inspected. Evidence is under `.work/theme/agent-guides/`; these are authored fixtures, not user data. This validates the guide UI and generated commands, not live registration or authenticated tool calls inside six third-party clients.
